다음은 온라인 쇼핑몰의 할인 API를 바꾸는 가상 사례다. 할인 API 구현을 먼저 시작한 뒤 프런트엔드가 다른 응답 형태를 기대하면, 테스트 파일이 있어도 체크아웃은 틀린 금액을 보여 줄 수 있다. API 계약을 늦게 정하면 두 작업자가 서로 다른 전제로 구현할 수 있다. 다음 실행에 대화 전체를 넘기는 대신, 어떤 계약이 활성인지와 무엇을 검증해야 하는지 전달해야 한다.

## 실패를 막는 네 단계

1. **레지스트리**는 작업과 결정의 색인이다. `DISCOUNT-042`가 활성 계약인지, 새 계약이 이를 대체했는지를 찾는다.
2. **선별 인수인계**는 다음 담당자에게 목표, 입력, 변경 범위, 금지 행동, 완료 증거를 주는 작업 계약이다. 관련 없는 과거를 모두 읽히지 않는다.
3. **의존 순서**는 가격 코드 소유자가 API 스키마를 합의한 다음 구현과 UI를 진행하게 한다.
4. **산출물 검증**은 파일 존재, 스키마 유효성, 테스트 통과, 할인 금액의 업무 규칙에 맞는지 판단을 구분한다.

| 기록 | 할인 변경에서 남길 내용 | 용도 |
|---|---|---|
| 레지스트리 | `DISCOUNT-042`, 활성·대체됨 상태 | 유효한 결정을 찾는다 |
| 작업 계약 | API 응답과 가격 코드만 변경 | 범위를 제한한다 |
| 실행 기록 | 테스트 입력·출력과 검토 결과 | 결과를 다시 확인한다 |
| 보류한 개선 사항 | 통화 반올림, 소유자·기한·계기 | 미룬 판단을 이어간다 |

검증할 때는 만료 쿠폰의 적용 거절과 같은 요청의 중복 할인 방지를 확인한다. 멱등성은 같은 요청을 다시 보내도 한 번 처리한 것과 같은 결과가 나와야 한다는 뜻이다. 구현자와 다른 검토자는 계약과 결과를 독립적으로 대조한다.

> 인수인계: 할인 계산과 API 응답만 변경한다. 통화 반올림은 가격 팀이 소유하며 다중 통화 출시 전 또는 2026-12-01에 다시 판단한다.

## 오래된 결정과 검토 비용도 관리한다

최근 기록만 검색하면 오래된 보안 제약을 놓칠 수 있으므로 계약에는 활성·대체됨 상태와 이유를 둔다. 아키텍처·보안·신뢰성 검토는 변경 성격에 따라 호출하고, 모든 작은 작업에 큰 절차를 강제하지 않는다. 역할과 실행 이력을 남기는 일은 모델의 영구 기억을 뜻하지 않으며, 이 방식의 생산성 향상은 여기서 측정하지 않았다.

| 확인 단계 | 할인 기능에서 확인할 것 | 이 증거만으로는 모르는 것 |
|---|---|---|
| 파일 존재 | 구현과 테스트 파일이 만들어졌는가 | 할인 금액의 정확성 |
| 형식 검사 | 약속한 응답 항목과 자료형인가 | 쿠폰 유효기간 판단 |
| 동작 테스트 | 만료 쿠폰 거절, 중복 할인 방지가 통과했는가 | 테스트하지 않은 업무 조건 |
| 독립 검토 | 실제 정책과 테스트의 기대값이 일치하는가 | 모든 장애 상황의 안전성 |

작업을 맡기기 전에는 검토 범위가 비용에 맞는지도 판단해야 한다. 안내 문구 수정에 결제 구조 전체 검토를 붙일 이유는 없다. 반대로 할인 금액이나 결제 요청이 바뀌면 보안과 중복 처리 검토를 생략하기 어렵다. 이것이 일을 시작하기 전의 비용 판단이다. 결과를 받은 뒤 약속한 조건을 통과했는지 보는 품질 판단과 분리해야 한다.

역할도 기록의 대상이다. '검토자'라는 이름만 남기는 대신 담당 범위, 사용한 지침 버전, 최근 판단과 그 근거를 연결하면 다음 실행이 같은 기준에서 출발할 수 있다. 오래된 역할 지침을 새 업무에 그대로 적용하지 않도록 버전과 유효 상태도 함께 확인한다. 내가 이 구조에서 얻고 싶은 것은 대화의 길이를 늘리는 효과보다, 누가 무엇을 근거로 결정했는지 다시 확인할 수 있는 상태다.
